# GedaTv performance pass — before/after (6 Nov 2026)

"Before" is commit `bb72800` (the last commit). "After" is the working tree
with this change. Both were built with `next build` and served with
`next start` on the same machine, with the same TMDB key. Numbers are
local: there is no Netlify CDN in front of either version, so real visitors
see extra network time on both.

## How it was measured

- Headless Chrome over the DevTools protocol, a fresh browser profile per run
  (empty cache, empty sessionStorage), 3 runs per version, alternating which
  version goes first. Medians are reported.
- Page loads use Lighthouse's mobile settings: 412×823 screen, CPU slowed 4×,
  150 ms round trip, 1.6 Mbps download.
- Search timings use a desktop window (1350×940, 40 ms round trip, 10 Mbps),
  because the navbar search box only exists at desktop widths.
- Both servers were warmed first, so TMDB answers come from the server's cache
  and the runs compare the two apps, not TMDB's speed that minute.
- "TBT" is the sum of each long main-thread task's time over 50 ms after
  first paint.

## Search

| | Before | After |
|---|---|---|
| Press Enter in the navbar → results on screen | 626 ms | **411 ms** (−34%) |
| Type and pause, no Enter → results on screen | never (Enter needed) | **280 ms** after the last keystroke |
| Open `/search?q=dune` → results visible (mobile) | 2,768 ms | **2,385 ms** (−14%) |
| Layout shift on that page (CLS) | 0.432 (poor) | **0** |
| Requests the browser makes for one search | 3 server-action POSTs, run one after another | 1 cacheable GET |
| Search box on phones | none | yes |

Largest Contentful Paint on the search page reads 2,056 ms before and
4,852 ms after, but the two aren't comparable. Before, the LCP element was the
SEO paragraph, visible during a brief flash of the empty "What do you want to
watch?" state; the results then pushed it down (the 0.432 layout shift).
After, the LCP element is a result poster, which on slow 4G finishes
downloading at ~4.8 s.

The TV page's extra 3 requests and 30 KB are the video player's code,
downloaded while the page is idle so that pressing Play doesn't wait. It used
to be part of the page's first download.

Home and Movies are within about 3% of each other. Both versions serve them
as prebuilt pages, which this change doesn't make faster. Home's first paint
is 36–44 ms later and TBT 8 ms higher, a small cost of the live-search code
in the navbar and the streamed lower half of the page.

## Fresh homepage render (server side)

A forced re-render of `/` (the hourly refresh), timed with curl:

| | Before | After |
|---|---|---|
| TMDB caches empty (3 cold restarts) | 285 / 228 / 229 ms (median 229) | 247 / 208 / 219 ms (median 219) |
| TMDB answers already cached (5 runs) | 36–68 ms | 40–65 ms |

From this machine TMDB answers in about 100 ms, so removing the wait (logos
no longer queue behind all 8 lists) saves only ~10 ms here. The gain grows
with TMDB's response time, but that wasn't measured.

## Not measurable locally

- Netlify CDN caching of `/api/*` and `/categories/*`, and the removed `www`
  middleware (an edge function that ran on every request). After deploying,
  run this twice and check that the second shows `hit`:
  `curl -sI "https://gedatv.netlify.app/api/search?q=dune" | grep -i cache-status`
- Behaviour while TMDB is slow or failing (stale answers kept, failed
  refreshes not cached).
